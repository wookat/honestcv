# R845 — a LinkedIn export in another UI language keeps its profile text

## Candidates measured first (production R844 bundle)

Three items sat at the top of the queue. Each was measured before any code was touched.

1. **`resumeStrength` vs `resumeHealth` verdict mismatch.** Re-measured on the retained
   114-record text corpus (`/home/ubuntu/qa/r776-text-replay.json`, script
   `/home/ubuntu/qa/r845-verdicts.mts`): the two verdict tiers differ on **5 / 114**
   records (`Strong / Getting there` ×2, `Getting there / Needs work` ×3), score gap
   p50 4 · p90 4 · max 31. The earlier handoff figure `4 / 116` could not be reproduced
   from any retained corpus and is superseded by this measurement. The two meters are
   documented as measuring different things (completeness vs writing quality, see the
   doc comments in `src/lib/guidance.ts`) and production labels them separately; no
   first-hand evidence of user confusion was found, so no wording change is made.
2. **Sticky-nav occlusion (R843 finding 2).** Only reproducible as an axe artefact at a
   particular scroll offset; no user-facing defect confirmed. Deferred, unchanged.
3. **LinkedIn export printed in a non-English UI language.** Confirmed defect — chosen.

## Evidence

The LinkedIn detector (`looksLikeLinkedInExport`) keys on layout markers that do not
depend on language: the `handle (LinkedIn)` row, the profile URL, `Page N of M`,
`Top Skills`. The specialized parser (`parseLinkedInText`) keys on **English** section
headings (`Summary`, `Experience`, `Education`, …). A profile LinkedIn printed in
another UI language therefore passes detection and is handed to a parser that never
finds a section: every line stays in the header and the result is a skeleton.

Controlled proxies (`/home/ubuntu/qa/r845-foreign/*.de.txt`, generated by
`/home/ubuntu/qa/r845-write-foreign.mts` from the three retained real LinkedIn text
extractions by substituting the section words, page marks, `Present`, and the tenure /
date vocabulary with German). These are **synthetic translated-heading proxies, not
real German exports**; real non-English exports were not available.

| fixture (frozen R844 parser) | summary | experience | education | e-mail | LinkedIn |
| --- | --- | --- | --- | --- | --- |
| Kenneth DE | 0 chars | 0 | 0 | — | — |
| Giovanni DE | 0 chars | 0 | 0 | — | — |
| Bhu DE | 0 chars | 0 | 0 | — | — |

The English originals parse fully (717 / 22 / 5, 728 / 7 / 1, 311 / 5 / 3). Forcing the
generic parser on the proxies kept the text but made new mistakes: the translated label
(`Zusammenfassung`) became the title, the opening paragraph was dropped, the wrapped
e-mail `kenslinkedin2@kennethadams.` / `com` was lost, `Las Vegas Metropolitan Area`
became the title, and `www.linkedin.com/in/` / `kennethadams (LinkedIn)` yielded a
handle-less URL.

## Design

Scope is deliberately narrow — *keep the text*, not *read German LinkedIn*:

- `parseLinkedInText` returns `null` when it never saw a main-column section
  (`Summary` / `Experience` / `Education`); `parseResumeTextInner` then falls through to
  the generic parser. Recognised English exports are unchanged.
- Generic parser, header phase:
  - a one- or two-word label the heading vocabulary does not know, sitting over a prose
    line (`isUnknownSectionLabel`), is not the title when the document has the LinkedIn
    layout; the paragraph under it is the summary (`underLabel`).
  - a long line the next line continues (`continuesPrevious`) opens the summary even
    when it starts with a capital — LinkedIn's narrow column wraps before a sentence can
    end; `/` joins the open-phrase set (`Program/` ↵ `Project Manager`).
  - `headerPlace` accepts `REGION_LINE_RE` (`… Metropolitan Area`).
  - e-mail: after the complete `EMAIL_RE` match, a domain that ends in `.` at a line end
    followed by a 2–6 letter TLD on the next line is rejoined.
  - LinkedIn URL: a URL that ends at `/in/` is completed from the `handle (LinkedIn)` row.

Rejected: translating `LI_HEADINGS` for the five product languages (broadens R845 into
multilingual LinkedIn parsing with no real fixture to validate against); keeping the
skeleton (misleading — the user sees an empty profile and no error).
